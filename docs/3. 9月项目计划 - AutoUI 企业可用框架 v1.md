# 2026 年 9 月项目计划 - AutoUI 企业可用框架 v1

> [!summary] 项目目标
> 在 9 月完成一套可重复执行、可并行、可诊断、可接入 CI 的 Web UI 自动化框架 v1。
>
> 项目不追求目录和抽象数量，而以真实回归流程、稳定生命周期、失败诊断和 CI 门禁作为完成标准。

---

## 项目背景与基线

AutoUI 当前已具备 pytest-playwright、基础 Page Object、YAML 参数化和 Context 配置等基础能力。

本项目以现有代表流程作为回归安全网，在保留 Playwright 原生 Locator、auto-waiting、`expect()` 以及 pytest-playwright 原生产物能力的前提下完成框架重构。

---

## 项目范围

### 本月交付

```text
模块化 pytest 框架骨架。
配置优先级、启动校验与 secrets 边界。
独立 BrowserContext、运行身份和并行隔离。
结构化日志、失败截图和 trace。
JUnit XML、Allure results 与 GitHub Actions 门禁。
串行、xdist -n 2、受控失败和 CI 验收记录。
```

### 本月不做

```text
不接入 Appium、移动端和 PC 自动化实现。
不创建 CommonDriver、BaseTestCase、Locator 包装层或二次等待层。
不建设测试平台、设备农场、账号池和复杂重试机制。
不为了未来多端预先创建 app/、pc/ 或空的抽象接口。
```

## 工程设计原则

### 真实需求驱动的文件与抽象

```text
不按“一个概念一个文件”拆分代码。

新增 .py 文件必须满足至少一项：
1. 它有独立职责，且与现有文件的依赖不同。
2. 它被两个或以上真实调用方复用。
3. 留在当前文件会导致 pytest、Playwright、配置或运行时职责明显混杂。

不因未来可能性创建空模块、空目录、空基类或空 Protocol。
当真实调用方出现后，再提炼 Component、Flow、runtime、evidence 等模块。
```

当前配置阶段只保留：

```text
autoui/core/config/settings.py
  配置读取、优先级解析、校验、Settings 构造。

autoui/plugins/options.py
  pytest CLI 参数、session 初始化和 settings fixture。
```

### 多端演进边界

```text
当前仅实现 Web。

未来 App / PC 可共享配置、运行身份、日志、证据和报告契约；
不提前统一 click、fill、Locator、等待、断言或 Driver。

只有多个平台出现经过验证的共同需求时，才提炼跨端契约。
```

### 依赖方向

```text
tests -> Web Pages / Flows -> pytest fixtures -> pytest-playwright
pytest plugins -> core config / runtime
core 不依赖 pytest、Playwright 或具体平台实现
```

目标：

```text
完成清晰的 Web 框架包结构。
实现 CLI > YAML 配置的运行配置优先级。
将账号、密码、token 限制为环境变量或 GitHub Secrets。

```

验收：

```text

缺少必填配置时，在 Browser 启动前清晰失败。

仓库、日志和输出中不出现明文 secrets。
```

## 阶段 2：BrowserContext、运行身份、原生产物与并行

目标：

```text
每个 pytest item 使用独立 BrowserContext。
建立 testrun_uid、worker_id 和 test identity。
建立 AutoUI 的运行身份，并确认 pytest-playwright 原生输出目录能够隔离每个测试项。
不重复实现 pytest-playwright 已提供的截图、trace 和产物目录管理。
使用 pytest-xdist -n 2 证明至少两个 worker 实际执行测试。
```

验收：

```text
串行与 -n 2 的结果一致。
不同测试不覆盖数据、日志、截图或 trace；产物目录由 pytest-playwright 的测试项输出路径隔离。
连续执行不读取上次残留状态。
```

---

## 阶段 3：失败证据、日志、报告与 CI

目标：

```text
统一关联结构化日志、截图、trace 与 pytest report。
使用 pytest-playwright 的 `--tracing`、`--screenshot` 和 `--output` 配置生成浏览器证据。
只有存在真实的自定义日志或元数据写入需求时，才通过原生 `output_path` 写入对应测试目录。
生成 JUnit XML 与 Allure results。
建立 GitHub Actions，在干净环境安装依赖、浏览器并执行并行回归。
失败时仍上传证据，但不掩盖测试失败退出码。
```

验收：

```text
CI 收集错误、未知 marker、安装失败和回归失败都会失败。
失败后可按测试项和输出目录找到完整证据。
JUnit、Allure results 与 CI artifacts 可下载和查看。
```

## 当前运行时设计

### 能力归属

```text
pytest-playwright
  负责 Browser、BrowserContext、Page 的生命周期。
  负责 trace、screenshot、video 的采集开关与测试项输出目录。
  通过 --tracing、--screenshot、--output 等原生参数控制行为。

autoui.plugins.options
  负责 AutoUI 自己的 CLI 参数、配置合并和 Settings 初始化。

autoui.plugins.web
  负责将 Settings 转换为 browser_context_args。
  负责提供 AutoUI 的 Page Object fixture。
  不读取 YAML，不管理 trace，不保存 screenshot。

autoui.plugins.runtime
  负责构造 ExecutionIdentity：testrun_uid、worker_id、nodeid。
  自定义日志或元数据写入 pytest-playwright 提供的 output_path。
```

### 产物策略

```text
CI / 本地命令
  --output=artifacts
  --tracing=retain-on-failure
  --screenshot=only-on-failure
          |
          v
pytest-playwright
  按测试项生成隔离输出目录，并在测试结束时保留对应证据
          |
          v
artifacts/
  <test-item-output>/
    trace.zip
    test-failed-1.png
    （可选）AutoUI 自定义日志或元数据
```

trace 提供操作时间线、页面状态和网络等诊断信息，是 v1 的主要浏览器失败证据。后续新增证据类型时，必须由明确的诊断需求驱动，并写入对应测试项的输出目录。

### 阶段 1 配置与生命周期进度（2026-08-12）

#### 已完成

- `conftest.py` 已注册 `autoui.plugins.options`，pytest 能发现 AutoUI 的 hook 与 fixture。
- `options.py` 已注册 AutoUI 参数：
  - `--site`：`cn`、`com`、`zawa`。
  - `--env`：`pre`、`beta`、`release`。
  - `--base-url` 复用 pytest-playwright 原生参数，不重复注册。
- 环境配置采用两个真实维度：站点 × 环境。
  - `environments/defaults.yaml`：默认站点、默认环境和公共浏览器配置。
  - `environments/targets.yaml`：每个 `site / environment` 组合的 `base_url`。
- `resolve_settings()` 已将配置来源合并为一个不可变 `Settings`：

```text
defaults.yaml 的公共字段
+ targets.yaml[site][environment] 的目标地址
+ CLI 覆盖
-> Settings
```

- 当前优先级：

```text
site：--site > defaults.yaml
environment：--env > defaults.yaml
base_url：--base-url > targets.yaml
```

- `pytest_sessionstart()` 在浏览器启动前只构造一次 `Settings`，保存至 `config.autoui_settings`；`settings` fixture 将同一份配置交给 `web.py` 的 `browser_context_args`。
- 已验证：默认配置、CLI 选择站点/环境、CLI 临时 URL 覆盖、未知站点/环境报错、缺少必填字段报错。
- 代表回归流程已串行通过；`pytest -n 2` 已确认两个 worker 实际执行参数化用例。

#### 配置“合并”与“分离”的边界

```text
配置值：在 resolve_settings() 内合并，最终只向下游提供一个 Settings。
配置来源：defaults.yaml 与 targets.yaml 分离，避免公共字段在 9 个站点/环境组合中重复。
配置消费：通过 pytest fixture 分离，web.py 不重复读取 CLI 或 YAML。
```

这三层并不冲突：分离来源与职责，是为了保证最终生成的 `Settings` 唯一且一致。
