# 2026 年 9 月项目计划 - AutoUI 企业可用框架 v1

> [!summary] 项目目标
> 完成一套可重复执行、可并行、可诊断、可接入 CI 的 Web UI 自动化框架 v1。
>
> 完成标准不在目录和抽象数量，而在真实回归流程、稳定生命周期、可读业务日志、失败证据和 CI 门禁形成闭环。

---

## 1. 交付范围

### v1 必须完成

```text
模块化 pytest 框架骨架。
CLI > YAML 的非敏感运行配置与启动校验。
环境变量 / GitHub Secrets 注入运行凭据。
每个 pytest item 独立 BrowserContext、运行身份和输出目录。
面向人的业务步骤 JSONL，以及测试级失败事件。
pytest-playwright 原生 screenshot、trace 和 output_path。
JUnit XML、Allure results 与 GitHub Actions 门禁。
串行、xdist -n 2、受控失败和 CI 验收。
```

### v1 明确不做

```text
不接入 Appium、移动端和 PC 自动化。
不创建 CommonDriver、BaseTestCase、Locator 包装层或二次等待层。
不解析 trace.zip 生成公司日志，不依赖 Playwright 内部 trace 格式。
不 monkey patch Page、Locator 或 Playwright 内部 Channel。
不建设测试平台、设备农场、账号池和复杂重试机制。
不为未来可能性创建空模块、空目录、空基类或空 Protocol。
```

## 2. 总体架构

```text
测试用例
  负责场景编排和业务验证
        |
        v
Web Page Objects / 必要时的 Flows
  负责有明确业务目的的页面行为
  通过 @business_step 输出业务步骤
        |
        v
pytest fixtures / hooks
  注入 Settings、ExecutionIdentity、Page、日志和报告上下文
        |
        v
pytest-playwright / pytest-xdist
  负责浏览器生命周期、Context 隔离、并行和原生证据
```

依赖方向：

```text
tests -> Web Pages / Flows -> Web step runtime -> Playwright
pytest plugins -> core config / runtime / logging
core 不依赖 pytest、Playwright、Allure 或具体页面对象
```

只有出现两个及以上真实跨页面调用方时才创建 Flow。普通页面内的组合操作继续保留在 Page Object 中。

## 3. Page Object 与业务步骤粒度

### 原子业务操作的定义

原子业务操作不是一次 `click()`、`fill()` 或 `wait`，而是：

> 具有一个明确业务目的、一个明确完成条件，并且调用者通常不会拆开使用的完整页面行为。

因此，一个 Page Object 方法可以包含多个 Playwright 调用和必要的等待、页面切换或成功确认。例如：

```text
搜索业务 = 输入业务名称 + 点击查询 + 等待结果刷新
启动业务 = 点击启动 + 等待新标签页 + 切换并确认页面就绪
上传图片 = 设置文件 + 等待上传完成 + 确认预览出现
```

满足以下条件之一时才继续拆分：

```text
子操作会被其他场景独立复用。
子操作有独立业务含义和独立完成条件。
方法包含多个可独立选择的业务分支。
一个失败事件已经无法说明失败发生在哪个业务阶段。
操作跨越多个页面，并形成可复用业务流程。
```

### 推荐写法

```python
class ConfigBusinessAndPublishAppPage:
    @business_step("配置业务页搜索业务：{biz}")
    def search(self, biz: str) -> None:
        self.search_input.fill(biz)
        self.query_button.click()

    @business_step("启动指定业务并切换标签页：{biz}")
    def start_business(self, biz: str) -> Page:
        with self.page.expect_popup() as popup_info:
            self.business_start_button(biz).click()

        business_page = popup_info.value
        business_page.wait_for_load_state()
        return business_page
```

测试用例只负责编排：

```python
config_page.search("订单管理")
business_page = config_page.start_business("订单管理")
expect(business_page).to_have_title(...)
```

组合方法可以调用其他带 `@business_step` 的方法。此时日志和 Trace 使用父子 step 层级；私有辅助方法默认不记录业务步骤，避免重复和噪声。

## 4. 配置与浏览器生命周期

### 配置来源与边界

```text
defaults.yaml
  默认 site、environment 和公共浏览器配置。

targets.yaml
  site / environment 对应的 base_url。

pytest CLI
  --site、--env，以及 pytest-playwright 原生 --base-url。

环境变量 / GitHub Secrets
  账号、密码、token、API key 等运行凭据。
```

优先级：

```text
site：--site > defaults.yaml
environment：--env > defaults.yaml
base_url：--base-url > targets.yaml
```

`resolve_settings()` 在 Browser 启动前完成读取、合并和校验，并构造不可变 `Settings`。`web.py` 只消费 `settings` fixture，不读取 YAML 或 CLI。

运行凭据不进入仓库配置、YAML 或 `Settings`；内部测试日志与报告允许记录明文凭据、输入数据和错误上下文。

### BrowserContext 与运行身份

```text
Browser：pytest-playwright session 生命周期。
BrowserContext：每个 pytest item 独立创建和关闭。
Page：由当前 item 的独立 Context 提供。
ExecutionIdentity：testrun_uid + worker_id + nodeid。
output_path：pytest-playwright 为当前 item 提供的独立产物目录。
```

AutoUI 不重复实现 Browser、Context、Page、截图或 Trace 生命周期。

## 5. 业务日志与 Playwright Trace

### 两类信息的职责

```text
AutoUI JSONL
  记录人能理解的业务步骤、测试结果、输入数据、成功/失败和耗时。
  是公司平台查看和聚合测试过程的主要来源。

Playwright Trace
  记录 Locator、底层 click/fill/goto、auto-waiting、DOM、截图、console 和 network。
  是失败时定位技术细节的深度诊断证据。
```

不把底层 Playwright 动作重复转换成公司业务日志，也不从 Trace 反向推断业务语义。

### `@business_step` 契约

v1 的装饰器只支持同步 Page Object / Flow 实例方法：

```text
标题支持 {参数名} 格式化。
自动读取并记录除 self 外的方法参数。
进入方法前发送 started。
成功时发送 finished 和 duration_ms。
异常时发送 failed、异常类型、消息和 traceback，然后原样抛出。
为同一步骤创建同名 Playwright tracing.group。
为同一步骤创建同名 Allure step。
嵌套调用使用 step_id 与 parent_step_id 建立父子关系。
```

装饰器只负责参数绑定和委托，实际生命周期由注入到 Page Object / Flow 的 Web step runtime 管理：

```text
ExecutionIdentity + output_path
        -> AutoUILogger

Page + AutoUILogger
        -> WebStepRuntime

@business_step
        -> JSONL started/finished/failed
        -> tracing.group(title)
        -> Allure step(title)
        -> 原始 Page / Flow 方法
```

### 日志输出

每个测试项只写自己的文件：

```text
artifacts/<test-item-output>/
  autoui-events.jsonl
  autoui-errors.jsonl
```

每行必须是独立、可解析的 JSON 对象，核心字段为：

```text
schema_version
timestamp
level
event_type
phase
message
testrun_uid
worker_id
nodeid
step_id
parent_step_id
data
duration_ms
error_type
error_message
traceback
```

`autoui-events.jsonl` 保存完整事件；`autoui-errors.jsonl` 只保存 ERROR 及以上事件。两者可以包含相同的失败事件。

底层输出采用 Python 标准库 `logging`、每测试独立 `FileHandler` 和 AutoUI 自定义 JSON formatter。v1 不需要多进程轮转日志：xdist worker 不共享测试项日志文件。

### 测试级失败

Playwright 动作异常之外，pytest assertion、fixture setup 和 teardown 失败也必须记录。通过 `pytest_runtest_makereport` 为 `setup / call / teardown` 生成 `test_outcome` 事件，并保持原始 pytest 退出状态不变。

## 6. 证据、报告与关联

本地和 CI 统一使用：

```text
--output=artifacts
--tracing=retain-on-failure
--screenshot=only-on-failure
```

产物结构：

```text
artifacts/<test-item-output>/
  autoui-events.jsonl
  autoui-errors.jsonl
  trace.zip                 # 失败时保留
  test-failed-1.png         # 失败时保留
```

关联规则：

```text
nodeid
  关联 JSONL、pytest report、JUnit 和 Allure test case。

output_path
  关联同一测试项的 JSONL、截图和 Trace。

step_id / parent_step_id
  关联组合业务步骤与内部子步骤。

testrun_uid / worker_id
  关联同一次串行或 xdist 并行运行。
```

JUnit 写入必要的 identity properties；Allure 使用相同业务步骤名称，并在失败时附加或链接 JSONL、截图和 Trace。

## 7. 模块职责

```text
autoui/core/config/settings.py
  YAML 读取、配置优先级、校验和 Settings 构造。

autoui/core/runtime/identity.py
  ExecutionIdentity 数据模型；不依赖 pytest 或 Playwright。

autoui/core/logging/autoui_logger.py
  事件 schema、业务事件封装和标准 logging 提交；不依赖 pytest 或 Playwright。

autoui/platforms/web/steps.py
  business_step 装饰器和 WebStepRuntime；连接 AutoUILogger、Trace group 与 Allure step。

autoui/plugins/options.py
  pytest CLI、session 配置初始化和 settings fixture。

autoui/plugins/runtime.py
  ExecutionIdentity、output_path、每测试 logger 生命周期，以及 pytest report 失败事件。

autoui/plugins/web.py
  Settings -> browser_context_args，并提供 Page Object / WebStepRuntime fixtures。
```

不保留通过 monkey patch 包装 Playwright 公共方法的日志插件。迁移完成后，底层动作诊断完全交给 Trace。


```text

同时写入 JSONL、Trace group 和 Allure step。
```

### 步骤 3：测试失败与报告关联

```text
通过 pytest_runtest_makereport 记录 setup/call/teardown 结果。

```

### 步骤 4：并行与 CI 门禁

```text

失败时始终上传 artifacts，但保留 pytest 非零退出码。
```

## 9. 验收标准

```text
pytest --collect-only -q --strict-markers 成功。
缺少必填配置时在 Browser 启动前清晰失败。
每个测试项拥有独立 BrowserContext、ExecutionIdentity 和 output_path。
测试用例只负责编排和断言，不编写日志基础设施代码。
Page Object 的 @business_step 能输出可读 started/finished/failed JSONL。
组合业务方法可以包含多个原生 Playwright 调用，Trace 中显示同名业务分组。
不修改 Page、Locator 或 Playwright 内部对象。
断言、setup、call、teardown 失败均能形成测试级错误事件。
串行与 -n 2 结果一致，不覆盖其他测试的日志或证据。
失败后可从同一输出目录找到 JSONL、截图和 trace.zip。
JUnit、Allure 和 CI artifacts 可以通过统一身份关联。
GitHub Actions 能阻止收集错误、未知 marker、安装失败和回归失败。
```

## 10. 架构决策

```text
ADR-001：当前只实现 Web，多端只保留配置、运行身份、日志和报告的演进边界。
ADR-002：非敏感运行配置采用 CLI > YAML；凭据只从环境变量或 GitHub Secrets 注入。
ADR-003：凭据不进入仓库配置、YAML 或 Settings；内部测试日志和报告允许记录明文值。
ADR-004：pytest fixture / hook 生命周期替代 BaseTestCase 与 CommonDriver。
ADR-005：BrowserContext、screenshot、trace 和 output_path 复用 pytest-playwright 原生能力。
ADR-006：公司日志记录业务步骤，Playwright Trace 记录底层技术动作，两者不重复承担职责。
ADR-007：业务步骤粒度按完整业务目的和完成条件定义，不按单次 Playwright API 调用定义。
ADR-008：@business_step 同时驱动 JSONL、Trace group 和 Allure step。
ADR-009：每个测试项独立写 JSONL，使用标准 logging FileHandler，不使用全局日志文件或多进程轮转。
ADR-010：不 monkey patch Playwright，也不解析其内部 Trace 格式。
ADR-011：Flow 只在真实跨页面复用出现后创建，不预先建设空抽象。
```
