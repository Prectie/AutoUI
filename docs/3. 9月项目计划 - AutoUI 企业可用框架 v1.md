# 2026 年 9 月项目计划 - AutoUI 企业可用框架 v1

> [!summary] 项目目标
> 使用一个真实的 DesignKit 回归场景，完成可重复执行、可并行、可诊断、可接入 CI 的桌面 Web 自动化框架 v1。
>
> pytest 提供权威测试结果，Allure 展示业务步骤，Playwright Trace 提供详细技术诊断。不再建设第三套 AutoUI 业务事件日志。

架构方向以 [ADR-0001](./adr/0001-separate-execution-results-and-artifact-viewers.md) 和 [ADR-0002](./adr/0002-adopt-allure-report-3-as-reporting-center.md) 为准，整体设计与 Module 边界分别以 [UI 自动化框架技术设计](./design/autoui-ui-framework-technical-design.md) 和[桌面 Web v1 模块设计蓝图](./design/desktop-web-v1-module-blueprint.md)为准。

## 1. 交付范围

### v1 必须完成

```text
模块化 pytest 框架骨架。
CLI > YAML 的非敏感运行配置与启动校验。
环境变量或 CI Secrets 注入运行凭据。
每个 pytest item 独立 BrowserContext 和 output_path。
DesignKit Page Object、Business Flow 与真实回归测试。
Business Flow 使用 Allure 原生步骤描述数量不固定的业务过程。
pytest-playwright 原生 screenshot、trace 和 output_path。
Trace 作为对应 Allure 测试项的标准附件。
JUnit XML、Allure 3 report 与 GitHub Actions 门禁。
串行、xdist -n 2、受控失败和 CI 验收。
```

### v1 明确不做

```text
不实现 AutoUI 详细 JSONL 业务事件流。
不接入 Appium、移动 Web、移动 App、桌面 App 或小程序。
不创建 CommonDriver、BaseTestCase、BasePage、Locator 包装层或二次等待层。
不解析 trace.zip，不依赖 Playwright 内部 Trace 格式。
不监听 Allure 的下划线内部模块。
不 monkey patch Page、Locator 或 Playwright 内部 Channel。
不建设测试平台、预设 Result Manifest、性能观测、设备农场、账号池或复杂重试机制。
不为未来可能性创建空 Module、空目录、空基类或空 Protocol。
```

## 2. 目标架构

```text
pytest test
    │
    ├──调用──> DesignKit Business Flow
    │               │
    │               ├──编排──> DesignKit Page Objects ──> Playwright
    │               │
    │               └──声明──> @allure.step ──> Allure Business Report
    │
    └──判定──> pytest Test Outcome
                   └──pytest-playwright trace.zip
                                  └──标准附件──> 同一个 Allure test result
```

依赖方向：

```text
tests -> DesignKit Flows -> DesignKit Pages -> Playwright
Business Flow -> Allure 原生步骤 Interface
pytest plugin -> Settings / pytest-playwright / Allure labels 与附件
AutoUI 通用框架不依赖 DesignKit、Baidu 或 Order Console。
```

## 3. Business Flow、Page Object 与测试

### Business Flow

Business Flow 组合一个或多个页面操作，形成可复用的业务操作。它直接使用 `@allure.step` 声明业务读者能理解的步骤名称：

```python
class ImageEditorFlow:
    @allure.step("进入图片编辑器")
    def open_editor(self) -> None:
        ...

    @allure.step("上传标准图片：{image_path}")
    def upload_standard_image(self, image_path: str) -> None:
        ...

    @allure.step("添加标题并应用随机 VIP 字体")
    def add_title_with_vip_font(self) -> None:
        ...
```

Allure 原生装饰器负责标题参数格式化、步骤层级、状态、耗时和异常记录。AutoUI 不再包装这套 Interface，也不把步骤同步为 Trace group。

### Page Object

Page Object 只封装 DesignKit 页面元素、状态和 Playwright 操作：

```text
构造函数只接收所操作的 Page。
不依赖 Allure、Trace、JSONL、pytest request 或步骤 runtime。
可以包含多个 click、fill、wait 和 expect，但不直接定义业务报告步骤。
返回 Business Flow 继续编排所需的 Page、Path 或业务结果。
```

当前 `CommonPage` 只处理 DesignKit 宣传弹窗，不属于通用框架。迁移时将该行为并入合适的 DesignKit Page Object，不保留“通用页面”命名。

### pytest test

测试用例只选择业务操作、提供场景数据并完成最终断言：

```python
def test_editor_add_title_vip_font_download(
    image_editor: ImageEditorFlow,
    output_path: str,
) -> None:
    image_editor.open_editor()
    image_editor.upload_standard_image(str(EDITOR_STANDARD_IMAGE))
    image_editor.add_title_with_vip_font()

    downloaded_file = image_editor.download_result(output_path)

    assert downloaded_file.is_file()
    assert downloaded_file.stat().st_size > 0
```

业务步骤数量由场景决定，不设固定个数。

## 4. 配置与浏览器生命周期

### 配置来源

```text
defaults.yaml
  默认 site、environment 和公共浏览器配置。

targets.yaml
  site / environment 对应的 base_url。

pytest CLI
  --site、--env，以及 pytest-playwright 原生 --base-url。

环境变量 / CI Secrets
  账号、密码、token、API key 等运行凭据。
```

优先级：

```text
site：--site > defaults.yaml
environment：--env > defaults.yaml
base_url：--base-url > targets.yaml
```

`resolve_settings()` 在 Browser 启动前完成读取、合并、校验并构造不可变 `Settings`。`autoui/plugins/web.py` 只消费 `settings` fixture，不读取 YAML 或 CLI。

### 浏览器生命周期

```text
Browser：pytest-playwright session 生命周期。
BrowserContext：每个 pytest item 独立创建和关闭。
Page：由当前 item 的 BrowserContext 提供。
output_path：pytest-playwright 为当前 item 提供的独立产物目录。
```

AutoUI 不重复实现 Browser、BrowserContext、Page、截图、视频或 Trace 生命周期。

## 5. 结果、报告与诊断证据

### pytest Test Outcome

pytest 的 passed、failed、skipped 和 error 是唯一权威结果。Allure 和未来测试平台只能呈现该结果，不能产生第二套判定。

### Allure Business Report

Allure 展示测试用例、业务步骤层级、步骤状态、耗时、异常和附件。Business Flow 的原生 `@allure.step` 是常规声明方式。

### Playwright Trace

Trace 展示 Locator、click/fill/goto、auto-waiting、DOM、截图、console 和 network，是桌面 Web 的目标专属诊断证据。它由 pytest-playwright 原生采集，并以 `application/vnd.allure.playwright-trace` 附加到对应 Allure 测试项；AutoUI 不解析 Trace 内部格式，也不与业务步骤做映射。

### 原生产物

本地和 CI 统一使用 pytest-playwright：

```text
--output=artifacts
--tracing=retain-on-failure
--screenshot=only-on-failure
```

视频按场景需要通过 pytest-playwright 原生配置启用。下载文件继续使用当前测试项的 `output_path`。

## 6. 目标目录与 Module 职责

```text
autoui/core/config/settings.py
  YAML 读取、配置优先级、校验和 Settings 构造。

autoui/plugins/options.py
  pytest CLI、session 配置初始化和 settings fixture。

autoui/plugins/web.py
  Settings -> browser_context_args，复用 pytest-playwright 生命周期。

autoui/plugins/allure_reporting.py
  注入稳定执行 labels，并将 Trace、截图和视频附加到对应测试项。

tests/web/designkit/pages/
  DesignKit 页面元素、状态与 Playwright 操作。

tests/web/designkit/flows/
  DesignKit 可复用业务操作和业务步骤声明。
```

迁移完成后，`autoui/platforms/web/pages/`、详细 JSONL logger/formatter、`WebStepRuntime`、Baidu/Order Console 演示代码和只服务于演示的 data plugin 不再存在。

## 8. 验收标准

```text
配置错误在 Browser 启动前清晰失败。
每个测试项拥有独立 BrowserContext 和 output_path。
DesignKit 测试只通过 Business Flow 表达主要业务过程。
Business Flow 使用原生 Allure Interface 声明业务步骤；Trace 保留独立的技术操作层级。
Page Object 构造函数只接收 Page。
pytest 是唯一权威测试结果。
不生成 AutoUI 详细 JSONL 业务事件。
不修改或 monkey patch Playwright 对象。
串行与 xdist -n 2 不覆盖其他测试的证据。
失败后可从对应 Allure 测试项找到并打开 trace.zip，且仍能找到原始 Trace 和 screenshot。
GitHub Actions 能阻止收集错误、未知 marker、安装失败和回归失败。
```

所有 Python、pytest 和 Playwright 验证统一使用 `.venv\\Scripts\\python.exe`。

### 2026-09-06 实施验收记录

- 单元测试 `10 passed`，全仓库 `11 tests collected`，旧 `business_step`、`WebStepRuntime` 和详细 JSONL 链路无残留引用；
- 仓库内 `chromium-1234` 可由 pytest-playwright 启动，`xdist -n 2` 受控浏览器验证 `2 passed`；
- 受控失败结果包含三个原生 Allure 业务步骤、失败截图和 `application/vnd.allure.playwright-trace` 附件；
- Allure Report 3.14.3 成功生成报告，并归入 `DesignKit CN · beta · Chromium · Windows` 环境；
- 使用 `.auth/designkit-cn-release.json` 登录态执行真实 DesignKit 场景，进入编辑器、上传图片、选择 VIP 字体和下载作品全部通过，结果为 `1 passed`；
- DesignKit 登录态支持目标相关默认路径和 `DESIGNKIT_STORAGE_STATE` 覆盖；缺少文件时在 setup 阶段快速失败，注入 storage state 后能够建立独立 BrowserContext；
- 认证回归的 Allure 结果包含四个通过的原生业务步骤，并正确生成 Allure Report 3；
- CI 使用 Allure 3 `allure run` 启动 pytest，能够生成报告并透传 pytest 非零退出码；实际远端 workflow 仍需配置 `DESIGNKIT_STORAGE_STATE_B64` Secret 并在代码推送后验证。
